# Matt Direct Dev Workflow

把「idea → ship」串成一条**前半交互、后半无人**的闭环，实现阶段是**直接交付**：对着 ticket 把交付物做出来，再复审。不走红绿循环。

与 `matt-dev-workflow` 共享前半段与编排骨架。分叉只在实现：那边每张票跑 `/implement`（内部是 `/tdd` + `/code-review` + commit）；这边每张票由一个新子代理直接做出交付物，收尾用 `code-review` 的两轴。

适用**常规、单会话级**、且不该测试先行的任务。要红绿循环走 `matt-dev-workflow`。超大雾化任务用 `/wayfinder`；只澄清、不做实现用 `/grill-me`。

## 组合

按阶段调用，不把相邻技能的实现路径混进来：

| 阶段 | 用 | 不用 |
| --- | --- | --- |
| 0 厘清 | `/grill-with-docs`（`grilling` + `domain-modeling`） | 实施 |
| 1 spec | `/to-spec` | 停下来问 seam |
| 2 tickets | `/to-tickets` | 停下来 quiz |
| 3 实现 | 新子代理，按 ticket **直接交付** | `/implement`、`/implement-spec`、`/implement-with-subagents`、`/tdd` |
| 3 收尾 | `code-review` 的两轴 | 用新测试代替复审 |
| 收尾 | 用户显式跑 `/retro`（见文末） | 自动调用它、或把它算进无人阶段 |

`/implement`、`/implement-spec`、`/implement-with-subagents` 的构建步骤都会调用 `/tdd`。直接交付不要走它们。

grill 里若冒出「需要跑一下才能回答」的问题，停下，建议 `/handoff` 出去 + `/prototype` 再 `/handoff` 回。这是对无人化的合理打断，交用户决定。

## 前置

- 假设 `/setup-matt-pocock-skills` 已跑过（仓库存在 `docs/agents/issue-tracker.md` 或 `## Agent skills` 块）。没有 → **停下**，让用户先跑它，不自行补。
- tracker 形态（本地 `.scratch/` / GitHub / …）以 `docs/agents/issue-tracker.md` 为准，照其约定落盘。

## 阶段 0 — 交互式厘清（grill-with-docs）

运行 `/grill-with-docs`，完整跑完 `grilling` + `domain-modeling`：

- 一次一问、每问给推荐答案；代码能查的事实自己查，决策才问用户。
- 边问边把术语写进 `CONTEXT.md`、把难逆决策写成 ADR。
- **不实施**，直到用户确认「已达成共识」。

### Grill 问题格式（强制）

每个问题必须是**编号多选题**，用户只需回复数字即可。禁止开放式、是非混搭、或「A/B/推荐/自由写」这类随机答法。

每问固定结构：

1. 一句问题（只问一件事）
2. **2–4 个互斥选项**，编号为 `1.` `2.` `3.` `4.`（最多 4 个；不要用 A/B/C、字母、emoji、复选）
3. **推荐项标 `(Recommended)`**，通常放在 `1.`
4. 最后一行固定写：`回复数字 1–N 即可；若都不合适，直接写你的答案。`

示例：

```
错误处理策略选哪种？

1. 失败即回滚整单，返回统一错误码 (Recommended)
2. 部分成功，成功项落库，失败项单独回报
3. 入队重试，超过 N 次再进死信
4. 仅记日志，调用方自行决定

回复数字 1–4 即可；若都不合适，直接写你的答案。
```

约束：

- **一次只出一题**；等用户回复后再出下一题。
- 用户回 `1` / `2` / `3` / `4`（或 `1.`）即视为选中对应项；不要再追问「你是说第几个吗」。
- 用户回自由文本时，按文本理解并确认后再继续。
- 不要把多个决策塞进一题；不要用「你觉得呢？」「有什么想法？」这类无选项问题。
- 仅当决策空间真无法枚举时才用自由输入，并先说明为何无法给选项。

这是本流程**唯一的交互阶段**。

**完成判定**：用户明确确认共识并给出 "开始 / go"。否则停在 grill。

## 切入无人阶段（go 之后）

用户一句 "go" 即把控制权交给自动阶段。**此后不再向用户提问**，除非命中「停止条件」。

进入前做两件一次性准备：

1. **落共识锚点**：把 grill 结论压成一句话目标 + 关键决策清单，作为 spec / tickets / 子代理的共同起点（spec 路径是它们的实际锚点）。
2. **定分支**：
   - 当前已在 **worktree 分支**（`git worktree list` 中 cwd 命中某 linked worktree 路径，即会话已处于独立分支）→ 就地提交，不开新分支。
   - 否则（在主仓库默认分支上）→ 先创建一个 feature 分支再开始，整条流程都在此分支提交。
   - 未经用户要求不 push / merge / rebase / tag / 改写历史。

## 阶段 1 — 自动出 spec（to-spec，非交互）

运行 `/to-spec` 的流程，但**覆盖其 "check seams with user"**：不停下问用户，按其规则自动决策 ——

- 选**最高**既有可观察边界，能用一个就不开新的；确需新边界时在最高点提议。
- 把所选边界、理由、以及「若用户复核后想改可改」的假设写进 spec 的 Testing Decisions。这里记的是**验收时从哪里观察行为**，不是一张必须先写的测试清单。

其余步骤（探索代码、用 glossary 词汇、遵守相关 ADR、套 spec 模板、发布、打 `ready-for-agent`）原样执行。

**完成判定**：`.scratch/<slug>/spec.md` 已落盘、含验收边界、已打 `ready-for-agent`。

## 阶段 2 — 自动拆 tickets（to-tickets，非交互）

运行 `/to-tickets` 的流程，但**覆盖其 "quiz the user"**：不停下问用户，按 tracer-bullet 规则自动决策 ——

- 每张是纵向完整切片、可独立验收、单上下文可装下。完成面是这条切片真实的验收证据，**不另加一层测试**来凑垂直。
- 先做 prefactoring 再切片；宽重构走 expand–contract。没有可预构的本地代码时，跳过 prefactor，直接切可验收的薄片。
- 自动给阻塞边，得出 frontier 顺序（blockers 全 done 的票优先；线性链即从 `01` 起）。
- 把粒度理由 + 假设写进各 ticket / 汇总。
- **控粒度防子代理超时**：单票应能在一次直接交付 + 一次两轴复审内收尾。若预估要多轮返工、多模块深改或 >1 次完整复审才能装下，继续拆票。

其余步骤（glossary 词汇、遵守 ADR、一票一文件、`ready-for-agent`）原样执行。不关不改任何父 issue。

**完成判定**：`.scratch/<slug>/issues/NN-*.md` 全部落盘、阻塞边齐全、frontier 顺序已定。

## 阶段 3 — 按 frontier 逐张直接交付（硬性，禁止主会话降级）

> **核心约束**：阶段 3 = 对每张 frontier ticket 派一个新子代理**直接做出该票的交付物**，再按 `code-review` 的两轴复审。
> 主会话（orchestrator）**不得**以「赶进度 / 工具慢 / 子代理半成品」为由，在主上下文里直接做这张票的交付并标完成。

直接交付的顺序是：读 ticket 的验收标准 → 把交付物做出来 → 用验收标准核对 → 两轴复审 → 有本地改动才 commit。测试不是驱动，也不是另一张必写的产物。仓库里已有、且能覆盖这次改动的检查，在改动了对应可执行代码时照跑；不要为了凑红绿而新写一套测试。

### 3.1 每张票的强制形态

frontier 上**每一张** ticket：

1. **派一个全新子代理**（独立上下文）。一票一代理，禁止复用上一票代理「接着改」。
2. 子代理启动提示必须显式包含：
   - 默认简体中文；不要输出思考过程
   - 你不是一个人在改，不要回退他人改动
   - **直接实现本 ticket**。不调用 `/implement`、`/implement-spec`、`/implement-with-subagents`、`/tdd`，不先写测试再补交付
   - spec 路径、本 ticket 路径、分支名、验收标准（从 ticket 与 spec 抄，不另发明）
   - 完成清单（见 3.2）
3. 子代理内做完这张票：
   - 按验收标准做出交付物
   - 改动了可执行代码、且仓库有对应门禁时：先跑本票相关检查，收尾跑该语言/包的全量门禁（如 `cargo test` / `pnpm test` / `npm test` / monorepo 对应 package）。纯记录类改动不跑这套门禁
   - 交付物本身不是本地代码改动时：逐条对照验收标准，把读回到的证据写进回报。不造一份本地代码来充当交付物
   - **两轴复审**（固定点 = 本票开始前的 HEAD；做法见 3.1.1）
   - 复审有必须修的问题 → 在本票内修到过，再复审一次
   - 本票在工作区留下改动时，在阶段 0 所定分支上 **commit**（标题遵守仓库 git 规范）。没有本地改动就不造空提交，把证据写进该 ticket 的评论
4. 子代理回报必须含：交付物是什么、验收证据、**两轴复审结论**、commit hash（或「无本地 diff」）、改动文件（或无）。缺任一项 = 未完成。
5. 主会话核验回报，并核对 `git log` / `git status` 与证据是否一致，才把 ticket 标 `done`，再启动下一张。

一张未过，**禁止**启动下一张。阻塞边未满足的票不启动。

### 3.1.1 复审

复审对象是**这张票的交付物**。两轴分开，不合并排名：

- **Spec**：交付物是否就是 spec / 本 ticket 要的。缺了什么、多了什么、做了但做错了什么。每条引用 spec 或 ticket 原文。
- **Standards**：交付物是否符合仓库里写明的、且适用于这类产物的规范。

证据按交付物的形态取：

- 交付物就是本地 diff → 完整运行 `/code-review`。固定点 = 本票开始前的 HEAD。Standards 含该 skill 的 smell baseline，仓库规范优先。
- 交付物不是这份 diff → **不要**跑 `/code-review` 的 git 步骤（空 diff 会在它第 1 步失败，也不能用一份无关 diff 冒充）。子代理按上面两轴审交付物本身。没有适用于该产物的书面规范时，Standards 写「无适用规范」，只保留 Spec 轴；不要把代码 smell 套到不是代码的产物上。

### 3.2 单票完成定义（缺一不可）

- [ ] 验收标准全部满足，且证据在回报里
- [ ] 交付物是直接做出来的，不是先写测试再补实现
- [ ] 该跑的仓库门禁已跑；不该跑的已说明，并有逐条验收证据
- [ ] 两轴复审已做：**Spec 通过**；Standards 通过，或明确「无适用规范」。只剩已记录的非阻断 nit，且不违反仓库门禁
- [ ] 本地改动已 commit，工作区无本票残留；或确认无本地 diff，证据已写入 ticket 评论
- [ ] 子代理回报完整

任一项缺失 → 该票 **未完成**，不得进入下一张，也不得进入最终验收「全部完成」口径。

### 3.3 主会话允许做什么 / 禁止做什么

**允许（编排）**

- 写 spec / tickets、定分支、更新 ticket Status 与证据评论
- 派发 / 等待 / 核验子代理结果
- 跑只读核验（`git status`、`git log`、复跑子代理声称的检查、核对回报里的证据）
- 按停止条件汇总交用户

**禁止（除非走 3.4 恢复协议）**

- 主会话直接做 ticket 的交付物
- 改走 `/tdd` 或 `/implement` 家族
- 子代理未完成时，主会话代 commit 半成品并标 done
- 「先全部做完，最后统一复审」
- 因等待超时、子代理慢，就改在主会话手做

### 3.4 子代理失败时的恢复协议（唯一合法降级）

仅当子代理 **明确失败 / 超时 / 半成品残留** 时，主会话按序处理，**禁止静默接手做完**：

1. **记录失败**：ticket `## Comments` 写明失败形态（超时 / 验收不过 / 复审不过 / 半成品路径）。
2. **清理或保全**：若工作区有半成品，要么 `git stash` / 丢弃到可复现状态，要么在评论中列出未提交文件；不得无说明混进下一尝试。票外已经造成的变更记入评论，不假装能在本地还原。
3. **重派一次**全新子代理，提示中附上失败原因与半成品状态，仍要求直接交付 + 两轴复审。
4. **第二次仍失败** → **停止整个自动阶段**，上浮该票 + 两次失败原因 + 已完成的前序结果，交用户裁决。
5. **禁止**主会话在第二次失败后自行做完并宣称流程成功。

唯一例外：用户在停止后明确说「主会话接手做这张票」——那是用户指令，不再算本 skill 的无人阶段。

### 3.5 工具摩擦不算豁免

下列情况 **不是** 跳过子代理直接交付的理由：

- 等待超时 → 拉长等待或轮询；仍失败走 3.4
- 子代理只交了部分产物 → 重派或停止，不由主会话补完
- 「相关检查已过」→ 不能代替验收证据与两轴复审

### 3.6 全流程结束后的总 gate（主会话）

所有 ticket 完成后，主会话再核对一次：

- 每张票的回报都含验收证据与两轴结论
- 改过可执行代码的票，其仓库门禁结果仍站得住
- `git status --short` 无本任务残留
- 最终验收汇总（见下）

若发现某票缺复审或缺证据，**回溯该票**为未完成，走 3.4 或交用户，不得在汇总里写成全部完成。

**阶段 3 完成判定**：frontier 每张票均满足 3.2；总 gate 通过。

## 停止条件（命中即停下交用户，绝不强行推进）

- grill 决策需可运行的答案 → 已在阶段 0 处理。
- 前置 setup 未就绪 → 停，让用户先跑 setup。
- grill → tickets 阶段逼近 smart zone（~120k）→ `/handoff`，在 fresh session 续跑，不降级硬撑。
- 某张 ticket：验收不过且子代理无法在范围内修好，或复审不过且无法自决修复 → **停整个自动阶段**，上浮该票 + 失败原因 + 已完成的前序结果。
- 3.4 恢复协议第二次仍失败 → 同上停止。
- 不跳过、不强提交坏产物、不留跳过检查的标记来假装通过。
- **不**把主会话手做的实现当成自动阶段成功。
- 同一张票按 3.4 连续两次新子代理均无法完成 → 停，交用户（避免无限换代理空转）。

## 最终验收（汇总交用户）

自动阶段结束（全部完成，或被停止条件打断）后，一次性汇总：

- spec 路径、tickets 清单 + 各自状态（含是否为直接交付：验收证据 / 两轴复审 / commit 或无本地 diff）
- 每张票：交付物、证据、**复审结论**、commit、改动文件
- 有本地提交时：整体 diff（`git diff <base>..HEAD`）与文件列表
- 若中途停下：卡点、原因、建议下一步

验收（合并 / 继续 / 返工）由用户决定；不替用户 merge / push。

## 收尾项 — `/retro`（用户触发，不属无人阶段）

最终验收交回用户后，**建议**用户跑 `/retro` 复盘本次会话。它**不是**阶段 4，也**不在**无人阶段内：

- `retro` 声明了 `disable-model-invocation`，只能由用户显式敲 `/retro`。主会话不得自行调用、不得代跑、不得把它写进阶段 3 的 gate 或任何「完成定义」。
- `retro` 第 4 步要把候选按严重度呈给用户，与「无人阶段不再提问」直接冲突，只能落在验收之后。

它复盘的是**环境**，不是代码：导航指针（`AGENTS.md`）、确定性检查（linter / hook / CI）、判断题规范（`CODING_STANDARDS.md`）、steering 文件瘦身、工具经济性。机械性错误一律落成确定性检查，别写成规范。

本流程已在生产它的原料：3.4 记录的失败形态、停止条件的卡点、各票复审结论与返工。

### 何时建议跑

- 命中过停止条件 → **强烈建议**
- 走过 3.4 恢复协议；有票返工 / 复审不过 / 交付物被推翻 → **强烈建议**
- 全程一次过、无返工 → 可跳过

### 给 `/retro` 的输入

- **本会话**（orchestrator 会话是主证据）。`/clear` 之前跑；已清空则让 `/retro` 指向本会话日志。
- `.scratch/<slug>/spec.md` 与 `issues/NN-*.md`，含各票 `## Comments` 里记录的失败形态与证据。
- `git log` 与 `git diff <base>..HEAD`。

### 边界与盲区

- 不改产品代码；不替用户 merge / push。
- 主会话只看到子代理的**回报**，看不到子代理会话内的工具经济性与导航摩擦。这两类发现证据不足时，`retro` 应写明缺口，不要编造；必要时由 `retro` 自己提议给子代理回报补字段。
