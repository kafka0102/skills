# Matt Dev Workflow

把 Matt Pocock 技能族的主流程（idea → ship）串成一条**前半交互、后半无人**的闭环：`/grill-with-docs` 厘清需求 → 用户一句 "go" → spec / tickets / 实现 / 提交全部自动完成 → 汇总交用户做最终验收。

适用**常规、单会话级**开发任务。超大雾化任务用 `/wayfinder`；只澄清无代码计划用 `/grill-me`。

## 前置

- 假设 `/setup-matt-pocock-skills` 已跑过（仓库存在 `docs/agents/issue-tracker.md` 或 `## Agent skills` 块）。没有 → **停下**，让用户先跑它，不自行补。
- tracker 形态（本地 `.scratch/` / GitHub / …）以 `docs/agents/issue-tracker.md` 为准，照其约定落盘。

## 阶段 0 — 交互式厘清（grill-with-docs）

运行 `/grill-with-docs`，完整跑完 `grilling` + `domain-modeling`：

- 一次一问、每问给推荐答案；代码能查的事实自己查，决策才问用户。
- 边问边把术语写进 `CONTEXT.md`、把难逆决策写成 ADR。
- **不实施**，直到用户确认「已达成共识」。

### Grill 问题格式（强制）

每个问题必须是**编号多选题**，用户只需回复数字即可。禁止开放式、是非混搭、或「A/B/推荐/自由写」这类随机答法。

每问固定结构：

1. 一句问题（只问一件事）
2. **2–4 个互斥选项**，编号为 `1.` `2.` `3.` `4.`（最多 4 个；不要用 A/B/C、字母、emoji、复选）
3. **推荐项标 `(Recommended)`**，通常放在 `1.`
4. 最后一行固定写：`回复数字 1–N 即可；若都不合适，直接写你的答案。`

示例：

```
错误处理策略选哪种？

1. 失败即回滚整单，返回统一错误码 (Recommended)
2. 部分成功，成功项落库，失败项单独回报
3. 入队重试，超过 N 次再进死信
4. 仅记日志，调用方自行决定

回复数字 1–4 即可；若都不合适，直接写你的答案。
```

约束：

- **一次只出一题**；等用户回复后再出下一题。
- 用户回 `1` / `2` / `3` / `4`（或 `1.`）即视为选中对应项；不要再追问「你是说第几个吗」。
- 用户回自由文本时，按文本理解并确认后再继续。
- 不要把多个决策塞进一题；不要用「你觉得呢？」「有什么想法？」这类无选项问题。
- 仅当决策空间真无法枚举时才用自由输入，并先说明为何无法给选项。

### 工具不可用与低风险问题

- 当前环境没有 `request_user_input`、或它在当前 mode 不可用时，不要为了低风险选择在 final 阻塞。
- 只有不可逆、安全 / 权限、数据模型 / 契约形状，或会明显扩大范围的决策才值得停下来问；列表列、按钮位置、文案、分页默认值这类可回退选择，直接采用推荐项，并在 spec 的「共识与默认决策」记录。
- 用户回复「怎么停了」「继续」「别问了」视为 go：把未答问题按推荐项落成假设，直接进入自动阶段，不再追问。
- 如果必须问且交互工具不可用，只在 final 提一个问题；用户答完立即继续。

这是本流程**唯一的交互阶段**。grilling 中若冒出「需要跑一下才能回答」的问题（状态 / 逻辑 / UI 必须看），停下，建议 `/handoff` 出去 + `/prototype` 再 `/handoff` 回 —— 这是对无人化的合理打断，交用户决定。

**完成判定**：用户明确确认共识并给出 "开始 / go"。否则停在 grill。

## 切入无人阶段（go 之后）

用户一句 "go" 即把控制权交给自动阶段。**此后不再向用户提问**，除非命中「停止条件」。

进入前做两件一次性准备：

1. **落共识锚点**：把 grill 结论压成一句话目标 + 关键决策清单，作为 spec / tickets / 子代理的共同起点（spec 路径是它们的实际锚点）。
2. **定分支**：
   - 当前已在 **worktree 分支**（`git worktree list` 中 cwd 命中某 linked worktree 路径，即会话已处于独立分支）→ 就地提交，不开新分支。
   - linked worktree 的 worktree 分支视为用户显式指定的分支；不得切回 `main`。
   - 否则（在主仓库默认分支上）→ 先创建一个 feature 分支再开始，整条流程都在此分支提交。
   - 未经用户要求不 push / merge / rebase / tag / 改写历史。

## 阶段 1 — 自动出 spec（to-spec，非交互）

运行 `/to-spec` 的流程，但**覆盖其 "check seams with user"**：不停下问用户，按其规则自动决策 ——

- **先按改动类型读 docs，再写验收标准**：照仓库 `docs/README.md`「读取顺序建议」的任务类型表（行名以该仓库 `docs/README.md` 的表为准，常见如 TypeScript / UI / 契约 / Git 提交…）确定必读文档并读完。spec 里凡涉及**机制选择**的验收标准（国际化取值方式、文件大小与拆分、测试层级、命令与 DTO 契约、提交格式等），必须引用具体 docs 条款（文件 + 规则原话）；引不出条款的，就不要把它写成验收标准。文档与你的直觉冲突时以文档为准。
- **可机械判定的口径写成逐条判过 / 不过**：取值集合、前缀 / 命名形状、长度上限、去重与归一化这类能机械判定的口径，验收标准要逐条写成能直接判「过 / 不过」的项（例如「前缀与实体名之间空白先归一化为单个空格」「实体名为空判不过」），不许压成一句概括，也不许留给实现与审查各自解释。反例：只写「前缀 + 实体名」这种概括，漏掉了「实体名非空」「前缀后空白先归一化」，实现与审查各解释一遍，多跑 3 轮修复 + 4 轮审查（2026-10-22 写作素材标签）。
- **布尔 query-style 字段写清空串语义**：仓库现有 `z.preprocess` 布尔 schema 通常把 `''` 当缺省；spec 必须写明「空串视为缺省 false」或明确拒绝空串，不能只写「拒绝其它非法值」。
- **计数 / 汇总 / 展示文案必须给样例**：凡验收标准涉及「显示数量」「共 N 条」「空数据时显示什么」，必须写出一个输入 → 输出样例（例：「在架 2 条 → 页签显示 `渠道 (2)`，表格仍渲染 8 行」）。只写「显示数量」会让实现与审查各解释一遍（2026-10-25 竞品详情页数量口径返工）。
- **软删除 / `deleted_at`**：涉及删除过滤、删除视图或恢复语义时，必须读 `docs/standards/backend/db-conventions.md`，并在 spec 引用具体条款与显式例外。
- 选**最高**既有 seam，能用一个就不开新 seam；确需新 seam 时在最高点提议。
- 把所选 seam、理由、以及「若用户复核后想改可改」的假设写进 spec 的 Testing Decisions。

其余步骤（探索代码、用 glossary 词汇、遵守相关 ADR、套 spec 模板、发布、打 `ready-for-agent`）原样执行。

**完成判定**：`.scratch/<slug>/spec.md` 已落盘、含 seam 决策、已打 `ready-for-agent`。

## 阶段 2 — 自动拆 tickets（to-tickets，非交互）

运行 `/to-tickets` 的流程，但**覆盖其 "quiz the user"**：不停下问用户，按 tracer-bullet 规则自动决策 ——

- 每张是纵向完整切片（schema / API / UI / tests 全打通）、可独立验收、单上下文可装下。
- **同 seam 的加字段先合并**：多个小需求若共用同一组 schema / contracts / repository / 页面文件，且都是同一类加字段或同一读模型扩展，合并成一张票；它们不是能独立落地的切片，拆开只会重复 migration、实现、审查、提交和全量门禁。只有能各自独立落地且文件不重叠时才拆。反例：同一竞品主表同时加评分与官网，拆成两票导致两次 migration、两次全量门禁和 fixture 范围混线。
- 先做 prefactoring 再切片；宽重构走 expand–contract。
- 自动给阻塞边，得出 frontier 顺序（blockers 全 done 的票优先；线性链即从 `01` 起）。
- 把粒度理由 + 假设写进各 ticket / 汇总。
- **分支 / 回落必须逐条验收**：spec 的 Implementation Decisions 里点名的每个分支、catch、回落、补偿或失败路径，都要在对应 ticket 里写成独立验收勾选项；不能只在 spec 里写「三条路径都覆盖」。验收项要能直接判过 / 不过，例如「P2002 指纹冲突复判分支有一个真实进入 catch 的 add 用例，断言原因写回 `正文已存在：88`」，而不是「三条路径都覆盖」。
- **spec 验收项 → ticket 逐条映射**：拆完票后按下面的 checklist 核对，不能只在 spec 里保留：
  - [ ] 逐条列出 `spec.md` 的验收项；
  - [ ] 每条都能定位到恰好一张 ticket 的验收清单；
  - [ ] 缺失的补票或补验收项，重复归属的合并或删重；
  - [ ] 完成后 spec 中不存在未归属的验收项。
- **控粒度，避免一张票装不下**：单票应能在约一次「聚焦测试 + 本票收尾全量」内收尾；同一 tree state 的全量只跑一次，后续审查 / 提交不重复全量；若预估需长时间全仓慢测、多模块深改或 >1 次完整 /code-review 才能装下，继续拆票。新 skill 要对照一个已有的大 skill 时，拆成纯函数一票、读写库一票。派实现时只点名要抄的文件和符号，不写「通读那个 skill」。这是上下文能不能装下，不是墙钟。不得据此给子代理设完成时限，也不得据此 interrupt 正在跑的子代理。

其余步骤（glossary 词汇、遵守 ADR、一票一文件、`ready-for-agent`）原样执行。不关不改任何父 issue。

**完成判定**：`.scratch/<slug>/issues/NN-*.md` 全部落盘、阻塞边齐全、frontier 顺序已定；每张票的验收项覆盖 spec 里该切片点名的所有分支 / 回落，缺一个就继续拆或补票；spec 的每条验收项都恰好落在一张票的验收清单里，缺失就补票或补验收项，不能只留在 spec。

## 阶段 3 — 按 frontier 逐张 /implement（硬性，禁止主会话降级）

> **核心约束**：阶段 3 的实现工作 = 对每张 frontier ticket **完整运行 `/implement` skill**。
> 主会话（orchestrator）**不得**以「赶进度 / 工具慢 / 子代理半成品」为由，在主上下文里直接改业务代码并 commit 冒充 implement。

### 3.1 每张票的强制形态

frontier 上**每一张** ticket：

> **tree state**：代码文件内容未再变化。实现代理跑全量后，审查只读、提交只 `git add` / `commit` 不改文件，视为同一 tree state；任何修复代理改了代码，就是新 tree state。

1. **派一个全新子代理**（独立上下文；`fork_context: false`）。一票一代理，禁止复用上一票代理「接着改」。
2. 子代理启动提示必须显式包含：
   - **第一句是红测试**：失败测试的路径，以及要跑的那一条命令。子代理的第一个工具调用是跑这条测试，或把失败测试写进点名文件。红测试文件落盘之前，不读 `/implement`、`/tdd` 或其它技能。落盘之后再读，只读本票 seam 用到的节。派发提示把红测试放在第一句，不把「先读完技能」放在它前面。
   - **结论优先，不设墙钟**：派发任务没有完成时限。材料足够逐条判过或不过时，把最终回报写完并结束本轮；材料不够就继续读和跑。心跳只提供可见性，不构成完成时限；不要用进展消息代替最终回报，也不要在派发提示里写 5–8 分钟、8 分钟静默或其他墙钟。
   - 默认简体中文；不要输出思考过程
   - 你不是一个人在改代码，不要回退他人改动
   - **必须按 `/implement` 执行到提交之前**，不是「随便改到绿」。这不改变红测试那一条的顺序：红测试文件先落盘，再读技能里本票用到的节。
   - spec 路径、本 ticket 路径、分支名、seam（从 spec Testing Decisions 抄）
   - 完成清单（见 3.2）
   - **进度用 `send_message` 发短状态**：至少覆盖红测试 / 实现完成 / 全量测试开始 / 结束；某个工具调用或测试批次可能长时间无输出时，在调用前和返回后各发一句。格式见 3.5.2。不要用 `follow-up_task` 催 root；最终回报仍按完整格式。若工具不支持 `send_message`，只在最终回报里写进展
   - 若本票的目标产物是外部平台上的已发布 Logic（不是本仓库代码）：提示里写上目标的 `functionRid` 与已发布版本。不要整份重读兄弟 Logic。artifact 已经很大时，把 flow 修改和发布回读拆成先后两段，仍是同一张票、同一个子代理。
   - 后到的进度催促只追加。整张票的完成清单仍然有效；第一片测试变绿不是本票结束。
3. 子代理内按 `/implement` 走到提交之前：
   - 在 spec 约定 seam 上 `/tdd`（红 → 绿；一片一片）
   - 定期类型检查 / 聚焦单测
   - **本票收尾跑一次全量测试**（项目约定的全量门禁，如 `cargo test` / `pnpm test` / `npm test` / monorepo 对应 package 全量；动到的语言/包都要跑。纯 docs 票除外；不得只跑「相关」测试就宣称完成）。这是本票的全量证据；同一 tree state 只跑这一次，后续审查 / 提交 / 总 gate 复用，修复改代码后重跑。
   - **不要在本上下文跑 `/code-review`，也不要自己下审查结论**
   - 先不 commit。回报里写明本票开始前的 HEAD SHA
4. 主会话另派一个**全新只读子代理**跑 `/code-review`（Standards + Spec 两轴，固定点 = 该 SHA）。审查提示里贴上本票 diff（或 `git diff` 命令加未跟踪文件列表）和本票验收清单，并写明：先读 diff，只打开审查清单里 diff 命中的行，能判过或不过就写结论。仓库若有审查必读清单（如 `docs/agents/review-standards.md`），把它的路径随固定点 / diff 命令 / 本票验收清单一并交给审查代理，由它按清单自选必读；**不要把规范清单重抄进派发提示**，避免造出第二份会漂移的事实源。审查代理据此一次写下 `## Standards` 与 `## Spec`，不再另搜规范文件，不再往下派子代理。能逐条判过或不过时，必须在同一次最终回报里写出这两段并结束本轮；还判不了就继续读命中的材料，不要停在「下一步」。开始写这两段时用 `send_message` 发一句话。票面验收或 Testing Decisions 点名的调用方，即使不在 diff 里，也打开该调用方再下 Spec 结论；「diff 没改这个文件」本身不是必须修。审查代理不改业务代码。审查默认只复跑本票聚焦测试与必要的类型 / lint，不重跑实现代理已跑过的全量套件；只有实现回报缺全量证据、或审查期间 tree state 变了，才补跑受影响包全量。不设审查墙钟。仓库审查清单里的「目标 5–8 分钟」只是阅读建议，不是停笔命令，也不是编排者 interrupt 的条件。中间进展消息不算最终回报，最终回报必须以 `## Standards` / `## Spec` 开头。
5. 审查有必须修的问题 → 再派一个新的实现子代理只修这些问题并重跑该票测试；若改了代码，tree state 已变，按 3.1 重跑全量。然后重新审查。通过后，由一个新子代理在阶段 0 所定分支上 **commit**（标题遵守仓库 git 规范）。提交提示里的「只提交」或「不要再跑测试」不能盖过仓库门禁：暂存区含代码时，提交前仍要跑仓库规定的检查（至少 pre-commit / 暂存文件的 biome / 类型检查 / 本票聚焦测试）。不重跑实现票已提供的全量套件；全量证据由实现票收尾提供。有 pre-commit 钩子时，钩子失败就还没提交。
   审查回报的「必须修」若编排者用证据复核后认为是误报，**不得照单改错，也不得直接标 done**：把反证与取证命令写进新派单，另派一次全新只读审查独立复核定论（同类误报常来自审查代理引用了与实现路径不同的函数或包）。
6. 实现回报必须含：交付、测试命令与结果、全量证据对应的 tree state（固定点 SHA + `git status --short`）、改动文件、未运行的命令与原因。审查回报必须含两轴结论，且保留 `## Standards` 与 `## Spec` 两个字面标题。commit 回报必须含 hash。缺任一项 = 未完成。
7. 主会话核验回报与 `git log` / 测试输出 / 全量证据的 tree state 后，才把 ticket 标 `done`，再启动下一张。

一张未 green，**禁止**启动下一张。阻塞边未满足的票不启动。

### 3.2 单票 green 定义（缺一不可）

- [ ] 验收标准全部满足
- [ ] `/tdd` 在约定 seam 上执行（非「先写光实现再补测」）
- [ ] ticket 验收项覆盖 spec 里该切片点名的所有分支 / 回落；Testing Decisions 点名的调用 / payload / 回落有对应测试
- [ ] 本票要求的全量测试通过，且回报写明命令 / 结果 / tree state；同一 tree state 不重复全量
- [ ] `/code-review` 由独立只读子代理完成，Standards + Spec **均通过**（或仅剩已记录的非阻断 nit，且不违反 AGENTS 门禁）。Testing Decisions 点名的调用、payload 或回落没有对应测试时，不算非阻断 nit，该票 not green。验收汇总能贴出该子代理回报里的字面标题 `## Standards` 与 `## Spec`。主会话自己写的审查结论不能代替这两段
- [ ] 已 commit，工作区无本票残留改动
- [ ] 子代理回报完整

任一项缺失 → 该票 **not green**，不得进入下一张，也不得进入最终验收「全部完成」口径。

### 3.3 主会话允许做什么 / 禁止做什么

**允许（编排）**

- 写 spec / tickets、定分支、更新 ticket Status 注释
- spawn / wait / 核验子代理结果
- 跑只读核验命令（`git status`、`git log`、必要时复跑聚焦测试确认子代理声称）；全量证据按 tree state 复用或补跑，不机械重跑
- 按停止条件汇总交用户

**禁止（除非走 3.4 恢复协议）**

- 主会话直接实现 ticket 业务代码
- 跳过 `/tdd`、`/code-review`、全量测试
- 子代理未 commit 时主会话代 commit 半成品并标 done
- 「先全部实现，最后统一 review / 测试」
- 因 wait 超时、shell 默认超时、子代理慢，就改在主会话手写
- 会话压缩、交接摘要或「接着做完」代替一张新的实现子代理。摘要里的半成品由新子代理从当前工作区接着做；主会话仍不写业务代码。

### 3.4 子代理失败时的恢复协议（唯一合法降级）

仅当子代理 **明确失败 / 按 3.5.1 已判定为空闲无产出 / 半成品残留** 时，主会话按序处理，**禁止静默接手写完**：

1. **记录失败**：ticket `## Comments` 写明失败形态（超时 / 测试红 / review 不过 / 半成品路径）。
2. **清理或保全**：若工作区有半成品，要么 `git stash` / 丢弃到可复现状态，要么在评论中列出未提交文件；不得无说明混进下一尝试。
3. **重派一次**全新子代理，提示中附上失败原因与半成品状态，仍要求完整 `/implement`。红测试仍是第一个工具调用。失败若是测试文件还没落盘，重派提示写明先把失败测试写进点名文件，再读技能。
4. **第二次仍失败** → **停止整个自动阶段**，上浮该票 + 两次失败原因 + 已 green 前序结果，交用户裁决。
5. **禁止**主会话在第二次失败后自行写完并宣称流程成功。

唯一例外：用户在停止后明确说「主会话接手实现这张票」——那是用户指令，不再算本 skill 的无人阶段。

### 3.5 工具摩擦不算豁免

下列情况 **不是** 跳过 `/implement` 的理由：

- `wait_agent` 超时 → 不是失败。代理仍是 running 时继续等，不因耗时走 3.4
- 子代理只交了部分文件 → 重派或停止，不主会话补完冒充 green
- 「相关测试已绿」→ 不能代替本票全量测试与 code-review

### 3.5.1 验证阶梯（防一上来全量慢测）

子代理**执行顺序**（收尾仍须满足 3.1/3.2 的全量要求）：

1. **聚焦**：本票相关过滤测试（如 `cargo test --lib <keyword>` / vitest 过滤）。
2. **本票相关类型 / lint**（若触及该语言）。
3. **有界加宽**：同 crate / 同 package 相关测试。
4. **全量**：本票收尾跑一次（见 3.1）；同一 tree state 只跑一次，后续审查 / 提交 / 总 gate 复用，修复改代码后重跑。跑之前在进度中声明。若存在已知超慢无关套件且本票未改到，须在回报写明未跑项与风险，但不得用此跳过本票真正相关的全量门禁。

派发出去的实现、审查、修复和提交代理，默认一直等到它交来完成清单要求的回报。不给这些派发任务设完成时限，也不因 `wait_agent` 超时、静默或耗时 interrupt 仍在 running 的代理。`wait_agent` 超时只说明这一轮邮箱没有新消息。禁止把几轮 30 秒或 60 秒超时相加后当成卡住。代理完成时，最终回报会经 `wait_agent` 送达。

超时后的默认动作是直接再调 `wait_agent`，不做别的；用户可见进展按 3.5.2 处理。超时本身就说明这一轮没有最终回报，不需要用 `list_agents` 再确认一遍。`wait_agent` 返回 FINAL_ANSWER 时，payload 就是最终回报，直接处理。只有准备催进度或 `interrupt_agent`（即要走 3.4）时，才调用一次 `list_agents` 看 `agent_status`；同一轮里指纹用 `git diff`、进程用 `ps`，不要为这两项再调用。该调用会把已完成代理的全文再附回来；本会话已经见过的完成回报视为已读，不引用、不复述、不据此重开审查。

工作区指纹是 `git diff` 的内容哈希，加上未跟踪文件的路径列表。已修改文件里的内容变了，`git status --short` 那一行可以不变，指纹会变。未跟踪目录在 status 里只显示一次 `?? dir/`，目录里的新文件算进路径列表。另看 `ps -eo pid,etime,command` 里有没有本票的 `vitest`、`tsc`、`pnpm test`、`pnpm lint`、`pnpm typecheck`、`cargo test`。

只读本票点名的文件、对照页或 skill，不会改指纹，也不会出现测试进程。代理状态仍是 running 时，这是在读，不是卡住，继续等。

死锁兜底不是任务时限，只用于代理已经不再工作。静默从最近一次邮箱消息、指纹变化、或测试 / 类型检查 / 编译进程起算。这三件事任一发生，静默重新计算。指纹变了就是还在写。

- 状态是 running：继续等。running 由准备催或中断那一刻的 `list_agents` 确认，不是每轮都查。只有连续 60 分钟没有任何邮箱消息、指纹没有变化、也没有本票的测试、类型检查或编译进程，才催一次。催的时候写明完成清单还缺什么。催完再等 30 分钟，仍然如此，才 `interrupt_agent`，然后走 3.4。
- 状态是空闲，且最终回报里没有本角色要求的内容（实现缺完成清单，审查缺 `## Standards` 与 `## Spec`）：先催一次把最终回报写出来。催完再等 30 分钟。仍然空闲且指纹没变，才 `interrupt_agent`，然后走 3.4。不要在空闲后的头几分钟就打断。

催进度时带上本票完成清单，并写明剩余切片还要做完。只描述下一片的催促，会被子代理当成整张票的新任务。催审查时只追加「把 `## Standards` 与 `## Spec` 写进最终回报」，不要把催促写成新的审查范围。

### 3.5.2 子代理可见性（事件驱动）

适用于实现、审查、修复、提交代理。进度消息只提供可见性，不改变完成判定，也不给代理设置完成时限。

- 子代理在开始、红测试、主体实现或审查完成、全量测试开始、全量测试结束、最终回报时发短消息。某个工具调用或测试批次可能长时间无输出时，在调用前和返回后各发一句；没有新事实时不发。
- 消息格式固定为：`进展：<角色> | 正在：<阶段> | 已完成：<...> | 剩余：<...> | 最近证据：<命令或结果>`。
- `wait_agent` 是事件等待，不是健康检查。宿主规定了分段超时就遵循；宿主允许更长等待时，用较长但仍有上限的等待，让 `send_message` 或最终回报唤醒，避免按秒轮询。
- 若宿主提供只返回运行状态或最近活动的 `agent_status` / heartbeat 查询，编排者可用它生成用户可见进展；不要用会把已完成代理全文回灌的 `list_agents` 当心跳工具。
- 每轮等待返回后：有新消息就立即转述；状态变化就汇报；连续没有新事实时合并为一句，不重复复述同一状态。用户询问进展时直接回答当前阶段，不中断仍在工作的代理。

### 3.6 全流程结束后的总 gate（主会话）

所有 ticket green 后，主会话做总 gate：

- 先核对最后一票的全量证据：命令、结果、tree state（HEAD + `git status --short`）。
- 若提交后 tree state 与全量证据一致（只有 commit，没有改文件），复用该证据，不重复全量。
- 若 tree state 变了或证据缺失，补跑一次全量。
- 仓库 AGENTS 门禁要求的静态检查 / 类型检查照常跑。
- `git status --short` 无任务残留。
- 最终验收汇总（见下）。

若发现某票其实缺 review / 缺全量测，**回溯该票**为 not green，走 3.4 或交用户，不得在汇总里写成全部完成。

**阶段 3 完成判定**：frontier 每张票均满足 3.2；总 gate 通过。验收汇总里每张实现票都有独立只读子代理回报中的字面标题 `## Standards` 与 `## Spec`。缺任一段，该票 not green，阶段 3 未完成。

## 停止条件（命中即停下交用户，绝不强行推进）

- grill 决策需 runnable 答案 → 已在阶段 0 处理。
- 前置 setup 未就绪 → 停，让用户先跑 setup。
- grill → tickets 阶段逼近 smart zone（~120k）→ `/handoff`，在 fresh session 续跑，不降级硬撑。
- 某张 ticket：测试红且子代理无法在范围内修好，或 `/code-review` 不过且无法自决修复 → **停整个自动阶段**，上浮该票 + 失败原因 + 已 commit 的前序结果。
- 3.4 恢复协议第二次仍失败 → 同上停止。
- 不跳过、不强提交坏代码、不留 `@ts-ignore` / `@ts-nocheck` / `eslint-disable` / 跳过测试。
- **不**把主会话手写实现当成自动阶段成功。
- 同一张票按 3.4 连续两次新子代理均无法 green → 停，交用户（避免无限换代理空转）。

## 最终验收（汇总交用户）

自动阶段结束（全部 green，或被停止条件打断）后，一次性汇总：

- spec 路径、tickets 清单 + 各自状态（含是否完整 `/implement`：tdd / 全量测 / code-review / commit）
- 每张票：交付、测试（含全量证据的 tree state）、commit、改动文件
- 把审查子代理的 `## Standards` 与 `## Spec` 两段原文放进汇总（可轻量清理措辞）。标题保持这两个字面量，两段都要在。编排者自己的结论写在这两段之后的单独一节，不并进、不重排两轴发现
- 整体 diff（`git diff <base>..HEAD`）与文件列表
- 若中途停下：卡点、原因、建议下一步

**完成判定**：每张实现票的汇总里都有独立只读子代理回报中的字面标题 `## Standards` 和 `## Spec`，其下是该轴报告；编排者结论在这两段之后单独成节。缺任一段 = 该票 not green，验收汇总未完成，阶段 3 未完成。主会话复述不算这两段。

验收（合并 / 继续 / 返工）由用户决定；不替用户 merge / push。

## 收尾项 — `/retro`（用户触发，不属无人阶段）

最终验收交回用户后，**建议**用户跑 `/retro` 复盘本次会话。它**不是**阶段 4，也**不在**无人阶段内：

- `retro` 声明了 `disable-model-invocation`，只能由用户显式敲 `/retro`。主会话不得自行调用、不得代跑、不得把它写进阶段 3 的 gate 或任何「完成判定」。
- `retro` 第 4 步要把候选按严重度呈给用户，与「无人阶段不再提问」直接冲突，只能落在验收之后。

它复盘的是**环境**，不是代码：导航指针（`AGENTS.md`）、确定性检查（linter / hook / CI）、判断题规范（`CODING_STANDARDS.md`）、steering 文件瘦身、工具经济性。机械性错误一律落成确定性检查，别写成规范。

本流程已在生产它的原料：3.4 记录的失败形态、停止条件的卡点、各票 review 结论与超时。

### 何时建议跑

- 命中过停止条件 → **强烈建议**
- 走过 3.4 恢复协议；有票超时 / 测试红 / review 返工 → **强烈建议**
- 全程一次过、无失败 → 可跳过

### 给 `/retro` 的输入

- **本会话**（orchestrator 会话是主证据）。`/clear` 之前跑；已清空则让 `/retro` 指向本会话日志。
- `.scratch/<slug>/spec.md` 与 `issues/NN-*.md`，含各票 `## Comments` 里记录的失败形态。
- `git log` 与 `git diff <base>..HEAD`。

### 边界与盲区

- 不改产品代码；不替用户 merge / push。
- 主会话只看到子代理的**回报**，看不到子代理会话内的工具经济性与导航摩擦。这两类发现证据不足时，`retro` 应写明缺口，不要编造；必要时由 `retro` 自己提议给子代理回报补字段。
